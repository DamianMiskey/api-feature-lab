# API Feature Lab

Backend API design, one technique per page. Every page calls a real endpoint of this site's own API, shows the raw request and response, explains it, and shows the code. A sibling of the [Vercel](https://vercel.djmiskey.com), [Cloudflare](https://lab.djmiskey.com) and [Motion](https://motion.djmiskey.com) labs.

**Stack:** Hono (API under `/api`, with `@hono/zod-openapi`) · Zod 4 · Drizzle ORM · Neon Postgres in production, PGlite (Postgres in WebAssembly) locally and in tests · Next.js 16 (App Router, Cache Components) for the pages · Tailwind CSS v4 · target: **https://api.djmiskey.com** on Vercel (Hobby).

## Run it

```bash
npm install
npm run dev        # http://localhost:3000, API at /api, in-memory PGlite (no setup)
```

Set `DATABASE_URL` (see `.env.example`) to use a real Postgres instead.

## Checks

```bash
npm run lint
npm run typecheck
npm test           # Vitest: the API through app.request() on PGlite (SSE streams included), registry, robots/sitemap
npm run build
npm run e2e        # Playwright against the build (starts `npm start` on :3300)
BASE_URL=https://api.djmiskey.com npm run e2e   # a deployment: read-only tests only
npm run worker:check   # bundle the Cloudflare Worker (no deploy)
npm run worker:deploy  # deploy it to api-cf.djmiskey.com (wrangler login first)
```

CI (`.github/workflows/ci.yml`) runs all of them on every pull request, with no secrets.

## Notes

- **One database API, two drivers.** With `DATABASE_URL`, Drizzle uses Neon's HTTP driver (one round trip per query, nothing to pool in a serverless function). Without it, an in-memory PGlite: real Postgres 17 in WebAssembly, so local dev, unit tests and CI need no database server and never touch real data. `ensureSchema` creates the table on first use (`create table if not exists`), with the title limits as `CHECK` constraints too. PGlite is listed in `serverExternalPackages` so its WebAssembly isn't bundled.
- **Hosting**: Vercel project `api-feature-lab` (team two-seats), connected to GitHub: every PR gets a preview, `main` deploys to production. Neon (`api-feature-lab-db`, Free plan, `iad1`) was added with `vercel integration add neon --plan free_v3 -m region=iad1 -e production --no-env-pull`: its variables exist **in production only**, so preview deployments run on in-memory PGlite and can never write to the live data, and `.env.local` never gets the production URL (local dev and `npm run e2e` stay on PGlite).
- **Errors** are always RFC 9457 Problem Details (`application/problem+json`): validation (422, with an `errors` list of field paths), unreadable JSON (400), missing resources and routes (404), and anything unexpected (500). Request bodies use `z.strictObject`, so unknown fields are rejected rather than silently dropped.
- **OpenAPI** is generated by `@hono/zod-openapi` from the route definitions and served at `/api/openapi.json`. The `/openapi` page renders it on the server (no third-party docs script, so the CSP stays `'self'`). API responses get `default-src 'none'`.
- **Pagination** is keyset on `(created_at, id)`: the cursor is opaque base64url JSON of the last row's `created_at` and `id`. `created_at` is set by the app (`new Date()`, millisecond precision) rather than Postgres' `now()` (microseconds), because the cursor carries it as an ISO string that must round-trip exactly. `?offset=` is supported only for the comparison demo, and combining it with a cursor is a 422.
- **Conditional requests** are hand-written in `src/api/http.ts` (not Hono's `etag` middleware) so `If-None-Match` and `If-Match` share one ETag function: a SHA-1 of the exact JSON. PATCH and DELETE re-check the version inside the SQL (`WHERE id = … AND updated_at = …`), so the check and the write are atomic. ETags are per representation, so a v2 ETag never matches a v1 write.
- **Versioning**: `/api/v2/…` and `API-Version: 2` give the same shape; the header form sends `Vary: API-Version`. `/api/v0/tasks` is a demonstration of a retiring version (fictional sunset date) with RFC 9745 `Deprecation`, RFC 8594 `Sunset` and `Link: rel="successor-version"`.
- **Auth** (`src/api/auth.ts`): `authenticate` runs on every request; no `Authorization` header is anonymous, but a bad one is always a 401, even on public endpoints. Keys look like `lab_` + 43 base64url characters (256 random bits); only their SHA-256 hash and a 12-character prefix are stored, and they expire after 24 hours. `POST /api/token` turns a key into an HS256 JWT (15 minutes, `iss`/`aud` verified); a revoked key's tokens stay valid until they expire. **`JWT_SECRET` must be set in production** (Sensitive); without it token issuance answers 503 there, while local dev and tests use a fixed development secret.
- **Rate limiting** (`src/api/ratelimit.ts`) keeps one counter row per client per window in `rate_limits`, incremented by a single `INSERT … ON CONFLICT … RETURNING` (atomic), and estimates a sliding window from the current and previous counts. Clients are keyed by API key/token when present, otherwise by `x-real-ip` (set by Vercel's network). Limits: writes 30/min anonymous, 120/min authenticated; key creation 5/hour; token exchange 20/min; the demo endpoint 5 per 10 s; score submissions 10/min; webhook inboxes 10/hour and pings 20/min. `LAB_WRITE_LIMIT`, `LAB_KEY_LIMIT`, `LAB_SCORE_LIMIT` and `LAB_INBOX_LIMIT` lift those limits for the test suites only. Hono's `/tasks/*` also matches `/tasks`: listing both patterns counted every write twice (caught by a unit test).
- **Leaderboards** (`src/api/routes/scores.ts`) serve the [Motion lab](https://motion.djmiskey.com)'s four games, plus a `demo` board this lab's own pages post to. Initials are three letters A–Z (nothing to moderate); Marble Maze ranks lowest time (milliseconds, all three levels), the rest highest score; ties go to the earlier score; the best 100 per game are kept. Scores can't be verified, since the games run in the browser: the per-game maximums only keep the boards plausible. Submissions are limited to 10 a minute per client. **CORS** is on for `/api/scores*` only, for `https://motion.djmiskey.com` and `http://localhost:*`, allowing the `Idempotency-Key` and `Last-Event-ID` request headers and exposing `ETag`, `Idempotent-Replayed` and the rate-limit headers.
- **Idempotency keys** (`src/api/idempotency.ts`, IETF draft): required on `POST /api/scores`, optional on `POST /api/tasks`. The key (a Structured Field string; bare values accepted) is scoped to the client (API key or IP) and claimed with one `INSERT … ON CONFLICT DO NOTHING`, so of concurrent requests with one key exactly one runs. The request fingerprint is a SHA-256 of method, path and body: the same key with a different body is a 422, a key whose first request is still running a 409 with `Retry-After`, and a finished one is replayed (status, `Content-Type`/`Location`/`ETag`, body) with `Idempotent-Replayed: true`. Only 2xx responses are stored; anything else releases the key so the client can fix the request and retry. Keys last 24 hours; a claim that never finished frees itself after a minute.
- **Webhooks** (`src/api/webhooks.ts`): an `events` table is the log; recording an event queues one `webhook_deliveries` row per subscriber. Messages follow [Standard Webhooks](https://www.standardwebhooks.com): `webhook-id` (`msg_<event id>`, the same on every retry), `webhook-timestamp`, and `webhook-signature: v1,<base64 HMAC-SHA256 of id.timestamp.body>` with a `whsec_` secret. The receiver checks the signature with `crypto.subtle.verify` (constant time), rejects timestamps more than 5 minutes off, and processes each message id once. Failed attempts retry after 2, 4, 8, 16 and 32 seconds; after 6 attempts the delivery is `failed`. Due deliveries are claimed by a single `UPDATE … SET next_attempt_at = now + 30 s` (a lease), and processed when an event is recorded and whenever a delivery log is read (Hobby crons run daily, so there's no background worker). Subscribers are demo inboxes on this same API, delivered to in-process through `app.fetch` (no visitor-supplied URLs, so no SSRF); they receive `score.submitted` for an hour after they're created (the 10 newest), and can be told to refuse each message 0–5 times to show the retries.
- **Server-Sent Events**: `GET /api/scores/stream?game=…` sends the board (`event: board`, `id:` the newest event id, `retry: 3000`), then polls the event log once a second and sends the board again when that game gets a score, with a `: keep-alive` comment after 10 quiet seconds. Each stream ends after 25 seconds (`LAB_SSE_SECONDS`); `EventSource` reconnects with `Last-Event-ID` and only the changes since are sent. Short streams, and pages that listen only while someone's looking, keep an open stream from holding a function (and Neon) awake. One known gap: `bigserial` ids are handed out at insert, not commit, so an insert that commits late with a lower id than one already streamed would be missed; a real system would read a commit-ordered log (logical replication) or re-read a short window.
- **API styles** (`/styles`): tRPC (`@trpc/server` 11, mounted with `@hono/trpc-server` at `/api/trpc`) and GraphQL (the reference `graphql` 17 package, code-first schema, at `POST /api/graphql`) reuse the REST endpoints' query helpers (`createTask`, `findTask`, `newestTasks`, `board`), so all three styles return the same data. The browser's tRPC client imports only `type AppRouter`, so no server code reaches the bundle, and `httpBatchLink` batches calls made together into one GET. The GraphQL handler follows GraphQL-over-HTTP: `application/graphql-response+json`, 400 when the request can't run (bad JSON, syntax, validation, over 4,000 characters, nesting deeper than 5; introspection fields aren't counted, so tools' standard introspection query works), and 200 with `errors` beside partial `data` once execution starts. Introspection stays on (the schema is public anyway). tRPC mutations share the REST writes budget; GraphQL has its own (60/min anonymous, 240 with a key). Neither appears in the OpenAPI document: tRPC clients get types from the router, GraphQL clients from the schema.
- **Cloudflare Workers** (`/portability`): the Hono app also runs as a Worker at https://api-cf.djmiskey.com (API only; the pages stay on Vercel). `worker/index.ts` is the whole entry point: it copies `CF-Connecting-IP` into `x-real-ip` (overwriting whatever the client sent, and dropping `x-forwarded-for`) so the rate limiter keys clients the same way on both platforms. `nodejs_compat` fills `process.env` from `wrangler.jsonc` vars and Worker secrets, so the app's configuration code is shared. `alias` swaps `@electric-sql/pglite` for a stub, keeping the WebAssembly out of a ~360 KB (gzip) bundle. Both copies use **the same Neon database**: `DATABASE_URL` and `JWT_SECRET` are Worker secrets (copied with `wrangler secret put`; the JWT secret was rotated to a fresh 256-bit value on both platforms when the Worker was added, so a token from either works on both). Free-plan limits shape the Worker's settings: 10 ms CPU and 50 subrequests per request, so `LAB_SCHEMA=skip` (no create-table statements per isolate; the tables already exist) and `LAB_SSE_SECONDS=15`. **Smart Placement** is on: the Worker starts near the visitor (each Neon query from Johannesburg takes ~240 ms), and Cloudflare moves it next to the database once it has seen enough traffic (`cf-placement: remote-…`). `GET /api/platform` reports platform, runtime, location and a timed `select 1`; it and `/api/scores` allow CORS from api.djmiskey.com, whose CSP `connect-src` allows api-cf.djmiskey.com. **The Worker isn't deployed by Git**: after changing `src/api`, run `npm run worker:deploy` (CI only checks that it bundles).
- **The live API is public**, so only the newest 200 tasks and 500 keys, the best 100 scores per game, the latest 1,000 events and 100 webhook inboxes are kept.
- **Accessibility and layout**: grid columns are `minmax(0, 1fr)` so wide JSON scrolls in its box instead of widening the page, and every scrollable code box is keyboard-focusable (axe checks both colour schemes in CI).

## Roadmap

- [x] **Phase 1: Foundations.** REST basics (tasks CRUD, status codes, Location), validation and Problem Details, generated OpenAPI docs, request explorer, Vitest + Playwright + CI
- [x] **Phase 2: HTTP semantics.** Cursor (keyset) pagination with `Link` headers and an offset-vs-cursor demo, ETags with 304 and If-Match/412 (atomic conditional update), versioning by URL and by header with `Vary`, and `Deprecation`/`Sunset` headers on a retired v0
- [x] **Phase 3: Auth.** API keys (shown once, SHA-256 hashed, scoped, 24 h expiry, self-revocation), key-for-JWT exchange (HS256, 15 min, issuer/audience checked), 401 vs 403 with RFC 6750 `WWW-Authenticate`, and a Postgres sliding-window rate limiter with IETF `RateLimit` headers on writes, key creation, token exchange and a demo endpoint
- [x] **Phase 4: Reliability.** Leaderboards for the Motion lab's games: `Idempotency-Key` on score submissions (replays, 409 and 422), signed Standard Webhooks with exponential-backoff retries and a dead-letter state, and a live leaderboard over Server-Sent Events with `Last-Event-ID` resume; CORS for the Motion lab's origin
- [x] **Phase 5: API styles.** REST vs tRPC vs GraphQL: the same questions sent all three ways from the page (request counts, bytes, raw exchanges, error shapes), tRPC batching and end-to-end types, GraphQL field selection with depth and length limits
- [x] **Phase 6: Portability.** The same Hono app on Cloudflare Workers (api-cf.djmiskey.com) and Vercel, sharing one Neon database; a page that asks both and writes on one, reads on the other
